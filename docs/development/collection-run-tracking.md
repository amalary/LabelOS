# Collection run lifecycle

Collection attempts reuse `CollectionRun` and `GovernanceService` for every registered
A&R / Analytics source. A documentation revision identifies the dataset version and
source through immutable, tenant-scoped provenance. Production creation and start
both enforce the existing current-documentation, terms, privacy and license checks.
The lifecycle does not add source-specific collectors or schedule external calls.

## State and history

- `queued` can become `running` or `cancelled`.
- `running` can become `completed`, `partially_completed`, `failed` or `cancelled`.
- Historical `succeeded` remains accepted as a successful terminal outcome; new
  workers should use `completed`. Existing histories are not rewritten.
- Failed and partially completed outcomes require an allowlisted `error_code`.
  Partial completion requires at least one written record. Rejected records can
  also occur during a completed collection (for example validation exclusions).
- Counts are cumulative within an attempt and cannot decrease. Written plus
  rejected counts cannot exceed seen counts. Retry counters start at zero.
- Identical terminal callbacks return the stored outcome without changing its end
  timestamp or adding audit/outbox events. A conflicting callback returns 409.
- Terminal attempts cannot be reopened, edited or deleted, including through SQL.

`run_key` is the workspace-unique external job/delivery identifier and idempotency
key. `job_id` optionally associates the attempt with an internal UUID job. Use a
new run key for each actual retry; redelivery of the same attempt uses its existing
key. Source and version IDs are resolved from the pinned documentation, not trusted
from worker input. Start/end timestamps are generated by the service and APIs
serialize them as UTC.

## Checkpoints and retries

`checkpoint_run` accepts cumulative counts, `expected_revision`, and a checkpoint
with numeric `offset`, numeric `page`, and optional UUID `cursor_reference`.
Only a running attempt can advance its checkpoint. Stale revisions conflict.
Opaque provider cursors must be stored separately in an approved secure store;
`cursor_reference` points there and is not the cursor itself.

Create a retry through `create_run` / POST collection-runs with `retry_of_id`, a new
`run_key`, and the original `documentation_id`, `production`, and `max_attempts`.
The predecessor must be failed or partially completed. Each predecessor has at
most one successor; the attempt number is assigned by the service. The retry
inherits its predecessor's checkpoint, but has independent counters, timestamps
and outcome. The default attempt budget is 3 (maximum 20). Optional `not_before`
sets the earliest permitted start, using a timezone-aware timestamp. The caller
chooses backoff and enqueues work; this service does not dispatch it. Changed or
revoked production eligibility can prevent a retry even when budget remains.

## Worker transaction contract

Construct `GovernanceService(session, workspace_id, actor=authenticated_actor)`
inside the trusted worker host. Actors must have the existing `governance.manage`
capability; no anonymous worker bypass or caller-supplied privilege is introduced.
A dedicated workload identity adapter remains the responsibility of the later
worker host, following the existing authorization boundary.

The caller owns commit/rollback. Create and commit the queued attempt before queue
dispatch, then start and commit before external collection. For each batch, persist
adapter data and call `checkpoint_run` in the **same transaction**, committing
only when both succeed. Finish the attempt and any final data writes in one
transaction. Roll back failed batch writes before recording the sanitized failure
in a fresh transaction, using counts from the last durable checkpoint. This keeps
partial successes visible without claiming rolled-back data. PostgreSQL row locks
serialize state changes; database guards also enforce history and retry invariants.

The service writes a durable `GovernanceActivity` and transactional realtime outbox
event for each accepted mutation. Both roll back with the data. Audit/outbox/log
messages contain generated IDs and fixed actions only: run keys, raw exceptions,
provider payloads, credentials, personal records and cursor contents are omitted.
Errors accept only fixed codes; free-form error text and checkpoint keys are
rejected. Workers must map provider failures to these codes and must not log the
raw exception or entire request/response. This deliberately removes sensitive
content instead of depending on pattern matching to recognize every credential.

## Protected APIs

Under `/api/v1/workspaces/{workspace_id}/governance`:

- POST `/collection-runs`: create or redeliver an attempt, including a retry.
- POST `/collection-runs/{id}/transitions`: start or record a terminal outcome.
- POST `/collection-runs/{id}/checkpoints`: atomically advance durable progress.
- GET `/collection-runs/{id}`: current status and pinned provenance.
- GET `/collection-runs`: paginated history; filters include `documentation_id`,
  `source_id`, `version_id`, `job_id`, `retry_of_id`, and `status`.

Reads require `governance.view`; writes require `governance.manage`. Every lookup,
list and retry is scoped to the workspace, even when resource IDs are known.

Migration `202610120400` preserves existing runs and transformation references.
On SQLite, constraint changes rebuild the table with foreign keys deferred and
verified before restoring the previous setting. PostgreSQL uses ALTER TABLE.
Downgrade refuses to discard any new tracking metadata or terminal state; restore
a compatible backup or retain this migration when tracking history already exists.
